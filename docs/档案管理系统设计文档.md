## 1. 系统定位与目标

面向企业财务档案场景的**电子档案管理系统**，管理对象为记账凭证、发票等票据影像及其结构化识别数据：

- **收**：后端按“一个子文件夹一个扫描批次”采集凭证/发票图片，安全入库后由 OCR 自动识别和拆分；
- **管**：分类、组卷（归档）、保管期限、密级管理；
- **查**：组合条件 + 全文检索，快速定位档案与票据；
- **用**：借阅申请、审批、归还、逾期提醒；
- **销**：到期销毁，审批 + 监销留痕。

**建设目标**：数据规范化（MySQL 8.0）、全流程留痕（审计日志）、权限可控（RBAC + 密级）、识别引擎可扩展、与现有骨架无缝衔接。

## 2. 骨架现状盘点（ledgerark）

### 2.1 模块结构（Maven 多模块）

```
ledgerark（父 POM：org.ledgerark:ledgerark:0.0.1）
├── ledgerark-admin      # 启动模块：@SpringBootApplication(scanBasePackages="org.ledgerark")、@MapperScan
│                        #    Web 入口 + Controller（web.controller.system）
├── ledgerark-common     # 公共模块（纯公共，不依赖业务）：Result / PageQuery / LoginUser、
│                        #    BaseEntity / ResultCode / BaseException
├── ledgerark-framework  # 框架模块：Sa-Token 拦截器、BCrypt 密码编码器、MyBatis-Plus 分页配置、
│                        #    全局异常处理（含 Sa-Token 异常）、登录服务（SysLoginService）、UserUtils
├── ledgerark-system     # 业务模块：Service / Mapper / DTO / VO + 业务实体（entity.sys）、

└── sql                  # 数据库脚本（sys_user.sql / sys_role.sql / sys_user_role.sql 完整建表）
```

依赖链：`admin → framework → system → common`（admin 只依赖 framework）。

**分层职责（沿用骨架现状）**：
- `ledgerark-common`：不依赖业务，纯公共（Result/BaseEntity/PageQuery/LoginUser/ResultCode/BaseException）；
- `ledgerark-framework`：横切能力（鉴权、异常、配置、工具、后续 AOP/文件/任务）；
- `ledgerark-system`：业务服务与持久层（Service/Mapper/DTO/VO）+ 业务实体/枚举/常量/异常；
- `ledgerark-admin`：Web 装配层（启动类、Controller、配置资源）。

## 5. 数据库设计（v2.4 目标模型）

### 5.1 设计边界与实现状态

数据库以 MySQL 8.0 为事务数据源，MyBatis-Plus 负责持久化与分页，Sa-Token 会话中的用户 ID 作为审计操作者。数据库只保存文件元数据、业务数据、OCR 结果与审计记录；图片原文件存放在受控文件系统或对象存储中，数据库通过 `storage_key` 引用，浏览器端不直接访问服务器物理路径。

本节使用以下状态标识，避免将设计稿误认为已实现功能：

| 标识 | 含义 |
| --- | --- |
| ✅ | 仓库已有实体与 DDL，当前骨架正在使用 |
| 🟡 | 仓库已有 DDL，但对应业务服务尚未完成 |
| 🆕 | v2.3/v2.4 目标模型，当前仓库尚无正式 DDL/实体，需要新增迁移脚本 |

| 数据域 | 当前基线 | v2.4 补充重点 |
| --- | --- | --- |
| 用户权限 | `sys_user`、`sys_role`、`sys_user_role` ✅ | 部门领导角色、角色数据范围、登录日志、Agent 审计 🆕 |
| 系统管理 | `sys_dept`、`sys_menu`、`sys_role_menu`、字典、操作日志 🟡 | 通知、用户通知、Agent 会话与引用记录 🆕 |
| 旧档案模型 | `biz_archive.sql` 中 11 张业务表 🟡 | 保留为迁移基线，不直接承担扫描拆分全过程 |
| 采集识别 | 仅 `biz_archive_file`、`biz_ocr_task` 🟡 | 采集源、扫描批次、不可变原文件、逐页 OCR 版本 🆕 |
| 拆分复核 | 无 | 凭证候选、页面编排、异常、人工复核任务 🆕 |
| 重复检验 | 仅文件 SHA-256 字段 | 重复案件、证据项、审批结论，重复数据不删除 🆕 |
| 正式档案 | 档案、凭证、发票、明细 🟡 | 当前版本、修改记录、流程历史、原文件关联 🆕 |
| Agent 检索 | 无 | 检索文档、分块、查询日志、档案引用及权限快照 🆕 |

### 5.2 命名、类型与通用字段规范

| 规则 | 约定 |
| --- | --- |
| 表前缀 | `sys_` 表示用户、权限、组织、日志与通知；`biz_` 表示采集、识别、档案及业务流程 |
| 主键 | `id BIGINT`，默认自增；Java 使用 `Long`，不在前端以浮点数处理，接口建议序列化为字符串 |
| 字符集 | `utf8mb4`，排序规则统一 `utf8mb4_unicode_ci` |
| 金额 | `DECIMAL(18,2)`；禁止使用 `FLOAT/DOUBLE` 保存金额 |
| 时间 | 新流水表采用 `DATETIME(3)`；Java 对应 `LocalDateTime`，业务日期采用 `DATE` |
| 状态 | `TINYINT` + Java 枚举；合法流转由 Service 层状态机校验，不依赖 MySQL `CHECK` 作为唯一保障 |
| JSON | OCR 原值、拆分计划、重复证据快照、版本快照采用 MySQL `JSON`；MyBatis-Plus 实体使用 JSON TypeHandler 或先映射为 `String` |
| 审计字段 | 可变业务实体继承 `BaseEntity`：`create_by/update_by/create_time/update_time/remark` |
| 逻辑删除 | 仅允许删除的可变实体增加 `del_flag` 并使用 `@TableLogic`；原文件、OCR 版本、流程历史、登录/操作/Agent 日志不做逻辑删除 |
| 乐观锁 | 人工复核任务、重复案件、档案主表等并发修改对象增加 `version INT`，实体使用 MyBatis-Plus `@Version` |
| 外键策略 | 核心数据默认 `RESTRICT`；仅纯关联表可 `CASCADE`。生产环境如因批量迁移关闭物理外键，仍须保留相同索引与 Service 层引用校验 |

`del_flag` 只表达“业务界面不可见”，不能用于抹除审计证据。已经归档的文件与版本必须通过作废、销毁等受控状态流转处理。

### 5.3 系统、角色与数据权限表

#### 5.3.1 现有核心表

- `sys_user` ✅：现有字段包含账号、密码、状态、`user_type`、`del_flag` 和审计字段；DDL 约定密码保存 BCrypt，但当前直接更新密码接口没有强制该约束。v2.4 迁移增加 `dept_id`、强制改密、锁定与乐观锁字段（§12.5）。
- `sys_role` ✅：已有 `role_key`、`data_scope` 字段，但运行时代码尚未加载角色或执行数据范围过滤；目标约束见 §12.5。
- `sys_user_role` ✅：已有用户与角色关联表及唯一键 `uk_user_role(user_id, role_id)`；当前注册不写该表，DDL 也没有外键和独立 `role_id` 索引。
- `sys_dept`、`sys_menu`、`sys_role_menu`、`sys_dict_type`、`sys_dict_item`、`sys_oper_log` 🟡：DDL 已在 `sql/sys_manage.sql`，后续补齐 Mapper/Service/API。

**当前 `sql/init_data.sql` 仍预置 `ADMIN/ARCHIVER/AUDITOR/USER` 四类角色，而运行时只在重置密码时读取 `sys_user.user_type`，两套模型尚未联动。**目标模型收敛为以下三类内置角色，业务判断以 `sys_role.role_key` 为准，不再扩大 `user_type` 的枚举职责：

| role_key | 角色 | 默认数据范围 |
| --- | --- | --- |
| `ADMIN` | 管理员 | 全部数据；可管理用户、角色、采集源、系统配置 |
| `DEPT_LEADER` | 部门领导 | 本部门及下级部门；可审批本部门重复案件与异常任务 |
| `USER` | 普通用户 | 本人创建、本人负责或被明确授权的数据 |

`sys_role.data_scope` 建议字典：`1=全部`、`2=自定义部门`、`3=本部门`、`4=本部门及下级`、`5=仅本人`。自定义部门范围增加 `sys_role_dept(role_id, dept_id)` 🆕，唯一键为 `(role_id, dept_id)`。

一期总览直接聚合 `biz_collection_batch`、`biz_ocr_task`、`biz_ocr_task_attempt`、`biz_recognition_page`、`biz_exception_record` 和 `biz_review_task`。当在线聚合不能满足响应目标时再新增 `biz_ocr_metric_daily`，按 `stat_date + organization_id + dept_id + source_id + engine_code + model_version + document_type` 汇总文件数、终态成功/失败、首次成功、重试、低置信度、转人工、平均/P95 耗时；唯一键覆盖全部维度，不保存可反推原始票据内容的字段。

### 5.6 凭证候选、页面编排与人工复核

#### biz_voucher_candidate（凭证候选）🆕

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| split_run_id / batch_id / candidate_no | BIGINT / BIGINT / VARCHAR(64) | 所属拆分运行、批次与候选编号；唯一键 `(split_run_id, candidate_no)` |
| start_order / end_order | INT | 在冻结文件清单中的起止顺序 |

| 字段 | 类型 | 说明 |

| candidate_id / split_run_id / recognition_page_id / source_file_id / source_page_no | BIGINT / INT | 候选、拆分运行、识别页、不可变原文件及文件内页码 |
| page_order | INT | 候选内页面顺序 |

唯一键 `(candidate_id, page_order)`、`(candidate_id, recognition_page_id)` 和 `(split_run_id, recognition_page_id)`。不得使用 `(candidate_id, source_file_id)` 唯一键，否则同一多页 PDF/TIFF 的多个页无法进入同一候选。人工拆分/合并必须新增拆分运行或候选修订，不删除 `biz_source_file`、`biz_recognition_page`。

MySQL 仍是档案事实来源。第一阶段先使用结构化条件查询和 MySQL 8 `ngram` 全文检索，不在当前库中强行保存向量字段。

### 5.11 状态编码建议

状态码应落入系统字典，并在 Java 中建立同名枚举。数据库保存数值，API 输出数值与可读标签。以下为 v2.4 摘要；采集稳定、拆分运行、失败案件和目录处置的完整状态以 §13.11 为准。

**批次 `biz_collection_batch.status`**：`0-待采集`、`10-文件入库`、`20-识别中`、`30-自动拆分`、`40-待人工复核`、`50-重复检验`、`60-已完成`；异常态 `91-部分失败`、`92-识别失败`、`93-已取消`、`94-源目录移动失败`。

**候选 `biz_voucher_candidate.status`**：`0-待识别`、`10-待拆分确认`、`20-待复核`、`30-待重复审批`、`40-已归档`；异常态 `91-识别异常`、`92-已驳回`、`93-确认重复`、`94-已作废`。

**重复案件 `biz_duplicate_case.status`**：`0-待分析`、`10-待人工确认`、`20-待审批`、`30-已结案`、`90-已取消`。

### 5.12 索引、幂等与约束策略

1. **批次幂等**：`(source_id, folder_fingerprint)` 唯一；同一文件夹被重新投放且内容变化时指纹变化，生成新批次并保留关联说明。
2. **原文件幂等**：`(batch_id, relative_path)` 唯一；SHA-256 仅建普通索引，重复文件也允许写入。
3. **OCR 版本幂等**：逐页结果以 `(source_file_id, recognition_version, page_no)` 唯一；任务号、请求号分别唯一；调用尝试以 `(task_id, attempt_no)` 唯一，防止消息重投产生重复任务或覆盖重试证据。
4. **拆分顺序**：`(candidate_id, page_order)` 唯一；`natural_order` 在批次开始后不可变。
5. **凭证业务键**：只建组合索引，不建唯一键；否则会违背“相同凭证号再次采集仍须保留并审批”的业务规则。
6. **发票号码**：同样不做无条件唯一；以 `invoice_code + invoice_no + 销方税号 + 金额 + 图像/OCR 相似度` 形成重复证据。
7. **版本唯一**：`(archive_id, version_no)` 唯一，`biz_archive.current_version_id` 指向当前版本；切换版本在事务中完成。
8. **工作台查询**：批次、复核任务、重复案件均建立 `(status, dept_id, create_time)` 或等价联合索引，列顺序以实际 SQL 过滤条件为准。
9. **大日志表**：登录、操作、Agent 查询与流程历史按时间建立索引；数据量达到千万级后再评估按月分区/冷热归档，避免初期过度设计。

### 5.13 事务、并发与文件一致性

- **采集事务**：创建批次、写入文件清单和 `biz_source_file` 元数据按批次短事务提交；文件复制成功并经 SHA-256 复核后才标记 `verify_status=成功`。
- **拆分事务**：候选、候选页面及异常记录一次性写入；失败时不改变批次的已冻结清单，可安全重跑并生成新的规则版本。
- **人工复核事务**：校验 `version` → 更新候选/任务 → 追加流程历史与变更记录，任一步失败全部回滚。
- **重复审批事务**：锁定重复案件 → 写结论 → 更新候选与档案关系 → 追加审批/流程流水；不执行文件删除。
- **归档事务**：创建 `biz_archive`、凭证/发票、档案版本、文件关联和检索待建标记；事务提交后再异步构建全文索引。
- **源目录移动**：确认所有文件已安全入库且批次业务处理完成后，移动至 `已处理/YYYY/MM/DD/{batchId}_{originalFolderName}`。目录移动属于数据库外部副作用，不与数据库事务强绑；失败写入批次移动状态和异常记录，由任务重试。
- **审计操作者**：从 Sa-Token Session 获取当前用户，写入 `create_by/update_by/operator_id`；异步任务使用明确的系统账号或 `operator_type=SYSTEM`，不得伪装成人工用户。

## 6. 核心流程设计（含代码落点）

### 6.1 归档流程

```
发现子文件夹 ─▶ 创建扫描批次并冻结自然排序 ─▶ 原文件安全入库/哈希复核
      └──────────────────────────────▶ 逐页 OCR（保留识别版本）
                                           ▼
                                    自动页面分类与凭证候选拆分
                                           ▼
                              字段冲突/未知页面/借贷不平人工复核
                                           ▼
                    业务键 + 图像/OCR 相似度重复检验与人工审批
                                           ▼
             建立正式档案、版本、文件关联及检索文档 ─▶ 批次完成
                                           ▼
                  原目录移入已处理目录（失败单独重试，不回滚档案）
```

拆分边界示例：`凭证001、凭证002、凭证001、发票` 归为**一个候选**并标记凭证号冲突；`凭证001、发票、凭证002、附件` 归为两个候选。事务边界详见 §5.13。

### 6.2 借阅流程（状态机 + 审批）

```
借阅申请（BorrowService.apply）→ 待审批
    → 同意：biz_archive 状态→已借出（borrow_status=1），借单→已批准
    → 驳回：借单→已驳回，档案不变
已借出 → 归还登记（BorrowService.return）：借单→已归还，borrow_status 复位
超期 → 定时任务置"逾期" + 通知，归还后仍归"已归还"
```

### 6.3 销毁流程（双审批留痕）

```
到期预警清单 → 销毁申请（DestructionService.apply，仅已归档且未借出）
    → 审批（DestructionService.approve，biz_approval_record 留痕）
    → 批准：登记销毁方式/时间/监销人 → 物理删除文件 → 档案状态→已销毁
    → 驳回：申请作废，档案保持已归档
```

### 6.4 OCR 识别流程（异步解耦）

```
提交任务（排队）→ 消费者以 version 乐观锁抢占（防重复消费）
    → 调用识别引擎 → 成功：追加 biz_recognition_page 识别版本并切换当前版本
    → 失败：记录 error_msg、retry_count 与 next_retry_time 后自动重试
    → 超时/重试耗尽：生成 biz_exception_record + biz_review_task，转人工介入
```

## 7. 权限模型设计（基于骨架现状）

- **已落地**：`sys_user`、Sa-Token 登录校验（只放行 `/sys/login/doLogin`、`/sys/login/register`）、登录返回 token、Session 中保存 `LoginUser` 和统一鉴权异常处理。`sys_user_role`/`sys_role` 虽已有表、实体与 Mapper，但尚未被登录、Session 或接口鉴权消费，不能算 RBAC 已落地。
- **规划**：
  1. 内置角色固定为 `ADMIN`（管理员）、`DEPT_LEADER`（部门领导）、`USER`（普通用户）；注册默认授予 `USER`，部门领导由管理员分配，不再扩展 `user_type` 枚举承载新角色；
  2. 菜单/权限点：`sys_menu`（菜单树 + `perms` 权限码 `模块:功能:操作`），角色-菜单关联 `sys_role_menu`；
  3. 接口级鉴权：`@SaCheckPermission("archive:review:approve")` 等权限注解 + Sa-Token 统一异常处理；
  4. 数据权限：`sys_role.data_scope + sys_role_dept`，MyBatis-Plus 数据权限拦截器根据核算主体、部门、负责人和密级追加条件；管理员看全部，部门领导看本部门及下级，普通用户看本人/被授权数据；
  5. 审计：用户启停用、重置密码、角色调整、复核、重复审批和 Agent 查询必须写入登录/操作/流程/Agent 审计表，密码与 token 永不写日志。

### 8.2 编码约定（对齐骨架）

- 实体：`@Data @TableName("biz_xxx")` 继承 `BaseEntity`；**需要逻辑删除的表加 `delFlag` 字段 + `@TableLogic`**（全局 `logic-delete-field: delFlag` 已配置，无需软删的表不加）；
- 并发：复核任务、重复案件、批次和档案实体的 `version` 字段使用 `@Version`；更新结果为 0 时返回“数据已被他人更新”，禁止静默覆盖；
- JSON：显式配置 `autoResultMap = true` 与 JSON TypeHandler，或先以 `String` 保存；不得依赖隐式对象序列化；
- 响应：一律 `Result<T>`；业务异常放 `system.exception`（已有 `UserException`，新增模块可建 `ArchiveException extends BaseException`）；
- 命名：接口 `I{Module}Service`、实现 `{Module}ServiceImpl`（沿用骨架 `ISysUserServiceImpl` 风格）；
- 入参/出参：DTO（含 jakarta validation 注解）/ VO（`@Builder`），禁止直接暴露实体；
- 分页：`PageQuery` + MyBatis-Plus `Page`，页大小上限 100（骨架已统一）；
- 权限：Controller 方法上加权限注解（规划）；当前用户取 `UserUtils.getCurrentUser()`。

## 9. 关键设计思路与决策

| # | 设计点 | 决策与理由（含骨架适配） |
| --- | --- | --- |
| ① | 子文件夹即批次 | `biz_collection_batch` 固化文件夹指纹和自然排序；启动后不再悄悄吸收新增文件，保证识别结果可重放 |
| ② | 原始数据不可变 | 原图片、SHA-256、OCR 历史版本只追加不覆盖；人工操作调整关联、主页面和档案版本，不删除证据 |
| ③ | 连续凭证页分组 | 遇到凭证页先继续归入当前候选，只有经过发票/附件区后出现的新凭证页才开始下一候选；默认最后凭证页为主数据页 |
| ④ | 凭证号冲突转人工 | `001 → 002 → 001` 仍是一个候选，记录冲突和复核原因，不按 OCR 号码强行拆成三份 |
| ⑤ | 重复数据先留后审 | SHA-256、感知哈希、OCR/版面相似度和业务键共同形成证据；凭证号与发票号不做会阻止入库的唯一约束 |
| ⑥ | 候选与正式档案隔离 | 自动拆分先落候选层，复核和重复审批通过后才生成 `biz_archive`，避免低置信 OCR 污染正式数据 |
| ⑦ | 档案聚合与版本 | 一个凭证档案对应一个档案根和零或一个凭证，可含多张发票/附件；每次修改生成档案版本和字段级变更记录 |
| ⑧ | OCR 双轨制 | 引擎原始 JSON、逐页结构化字段与人工校正后的正式字段并存，既可追溯又便于统计计算 |
| ⑨ | 状态机 + 流程历史 | 当前状态保存在业务表，所有流转追加到 `biz_workflow_history`；Service 层校验合法流转 |
| ⑩ | 逻辑删除与销毁分离 | `del_flag` 只用于允许软删的实体；审计、原文件、识别版本不软删，物理销毁必须经过审批并留下台账 |
| ⑪ | 数据范围前置 | 核算主体、账套、部门、负责人落在聚合根/批次；MyBatis-Plus 在查询层过滤，Agent 检索同样先鉴权再召回 |
| ⑫ | Agent 可引用、可审计 | 每次查询保存权限快照、模型、耗时、回答摘要和引用档案；第一阶段只读，回答必须带内部资源引用 |
| ⑬ | 全文检索分层 | 先以 MySQL 8 `ngram` + 结构化索引完成一期；语义检索后续接外部向量索引，MySQL 只保存 `embedding_ref` |
| ⑭ | 文件与数据库最终一致 | 源目录移动是事务外副作用；归档先提交，移动失败记录状态并重试，不能因移动失败回滚已校验数据 |
| ⑮ | 并发控制 | 批次、复核任务、重复案件、档案使用 `@Version` 乐观锁；调度任务以唯一请求号和状态抢占实现幂等 |
| ⑯ | 骨架适配 | 继续复用 Java 21、Spring Boot 4.1、MyBatis-Plus、Sa-Token、BCrypt、`Result<T>` 与统一异常体系 |

## 11. 风险与注意事项

1. `sql/biz_archive.sql` 是旧档案模型基线，不能在已有数据的共享环境中直接重跑，也不能在未调整唯一约束前承接“重复但保留”的新规则。
2. 目录扫描只能由有权限访问服务器/NAS/共享目录的后端进程完成；Web 页面只能配置采集源、查看状态和发起重试。
3. 原文件入库必须先复制、计算并复核 SHA-256，再允许移动源目录；跨磁盘移动应按“复制 → 校验 → 删除源”的补偿流程实现。
4. OCR 置信度不足时不得自动归档；页面分类、凭证号冲突、借贷不平和疑似重复均应生成可追踪的异常/复核任务。
5. `voucher_no`、`invoice_code + invoice_no` 不得设置阻止重复记录写入的唯一约束；重复控制由案件与审批流程承担。
6. Agent 查询必须复用与普通检索相同的数据范围，日志不得记录密码、token、完整身份证号或未脱敏银行卡号；引用记录必须能追溯到档案版本。
7. MyBatis-Plus 的 `@TableLogic`、`@Version` 和 JSON TypeHandler 均需通过集成测试验证，特别关注批量更新与自定义 SQL 是否绕过插件。
8. Spring Boot 4.1.0 较新，Sa-Token/MyBatis-Plus 已选用 boot4 适配依赖；新增 Flyway、OCR SDK、对象存储或检索组件时需先验证 Java 21 和 Boot 4 兼容性。
9. 所有 BIGINT ID 返回前端时应避免 JavaScript 精度丢失；Vue/TypeScript 模型建议按字符串接收 ID。
10. 生产迁移必须具备数据库备份、文件清单与哈希校验报告，以及从新表回退到旧读路径的预案。

## 12. 用户管理与 OCR 识别工作台专项设计（v2.4）

### 12.1 当前实现边界

本专项设计以 2026-08-24 当前工作区为依据。现状不是完整的用户中心或 OCR 系统：

| 能力域 | Java 运行时 | 数据库脚本 | 结论 |
| --- | --- | --- | --- |
| 登录认证 | 登录、注册、登出、重置密码、修改密码已存在 | `sys_user` 已有 DDL | 已有开发骨架，仍有权限与密码安全差距 |
| 用户管理 | 列表、分页、逻辑删除、直接更新密码已存在 | `sys_user`、`sys_role`、`sys_user_role` 已有 DDL | 部分实现，不是完整 RBAC 用户中心 |
| 角色/部门/菜单 | 角色仅列表、分页；无角色分配和运行时鉴权 | `sys_dept`、`sys_menu`、`sys_role_menu` 仅有 DDL | SQL 骨架，尚未被业务代码消费 |
| OCR | 无实体、Mapper、Service、Controller、调度器、引擎配置或文件存储实现 | 旧 `biz_archive_file`、`biz_ocr_task` 有 DDL | 仅旧模型基线，不能视为已实现 |
| 工作台 | 无后端聚合接口；当前仓库也无前端项目 | 目标通知、复核、汇总表尚未落地 | 全部为目标设计 |

旧 `biz_archive_file.archive_id NOT NULL` 要求“先有正式档案再识别”，且文件与 OCR 任务使用级联删除；这与“先采集、识别、复核，再归档”和“原始证据不可变”的目标冲突。v2.4 必须新建采集/OCR 表并迁移，不能直接扩写旧表继续双写。

### 12.2 用户管理功能设计

#### 12.2.1 功能与接口

| 功能 | 目标接口 | 权限 | 核心规则 |
| --- | --- | --- | --- |
| 用户分页筛选 | `GET /sys/user/page` | `system:user:list` | 支持账号、昵称、工号、部门、角色、状态、创建时间；固定排序，返回部门/角色摘要和 OCR 待办聚合数 |
| 用户详情 | `GET /sys/user/{id}` | `system:user:query` | 不返回密码、token、密码历史；按管理范围过滤 |
| 新增用户 | `POST /sys/user` | `system:user:add` | 用户名/邮箱唯一；密码只接收一次并立即 BCrypt；事务内分配默认部门/角色 |
| 编辑资料 | `PUT /sys/user/{id}` | `system:user:edit` | 可修改昵称、工号、邮箱、手机、性别、头像、备注；账号名变更需单独权限和审计 |
| 启用/停用/解锁 | `PUT /sys/user/{id}/status` | `system:user:status` | 禁止停用自己和最后一个有效管理员；停用/锁定解除均记录原因，停用后使全部会话失效 |
| 分配部门与角色 | `PUT /sys/user/{id}/roles` | `system:user:assign` | 校验角色、部门有效状态；事务内替换关联；不得越过操作者可管理的数据范围 |
| 管理员重置密码 | `POST /sys/user/{id}/reset-password` | `system:user:resetPassword` | 生成一次性随机凭据或重置链接；BCrypt 入库；置 `must_change_password=1`；全部会话失效 |
| 本人修改密码 | `POST /sys/login/changePassword` | 已登录本人 | 用户 ID 取当前 Session，不接受客户端指定；必须 BCrypt 验证旧密码，再校验新密码策略 |
| 转交 OCR 待办 | `POST /sys/user/{id}/transfer-tasks` | `system:user:transferTask` | 停用或删除复核人员前，原子转交其活动 `biz_review_task`，记录接收人和原因 |
| 逻辑删除 | `DELETE /sys/user/{id}` | `system:user:delete` | 先校验任务、管理员保护和引用关系；只置 `del_flag=1`，不删除审计、档案或识别记录 |
| 操作审计 | 随业务接口自动记录 | `system:audit:list`（查询） | 记录操作者、对象、前后值摘要、原因、结果、IP、request_id；密码和 token 永不入日志 |

当前 `POST /sys/user/updatePassword` 应标记废弃并尽快下线：它只要求登录、可指定任意用户且不保证 BCrypt。当前 `resetPassword` 使用固定 `123456`，`changePassword` 未验证旧密码，也都不能作为生产方案保留。

#### 12.2.2 生命周期与权限规则

目标用户状态：`0-正常`、`1-停用`、`2-锁定`、`3-待激活`；当前 Java 枚举只有 `0/1`，迁移后需同步 DTO、枚举、字典与登录判断。登录失败锁定是安全状态，不等同于管理员停用；超过锁定时间可自动恢复，管理员也可执行解锁。

用户管理写操作统一执行以下顺序：

1. Sa-Token 登录校验和 `@SaCheckPermission` 功能权限校验；
2. 根据角色数据范围校验操作者是否能管理目标用户；
3. 校验最后一个管理员、自操作保护、活动 OCR 待办和乐观锁版本；
4. 在事务内更新用户与关联表，并追加操作审计；
5. 事务提交后执行 Sa-Token 踢下线或会话失效；失败时写补偿告警，不回滚已提交的安全状态。

登录标识建议只允许唯一的 `user_name` 或 `email`，不再使用非唯一昵称登录。注册、登录和数据库长度统一为用户名 3～50 位；识别为邮箱时按邮箱规则校验，不套用用户名 20 位上限。Controller 必须启用 `@Valid`，`Long userId` 使用 `@NotNull` 而不是 `@NotBlank`。

### 12.3 OCR 识别工作台功能设计

#### 12.3.1 页面信息架构

工作台是 OCR 运行与人工处置入口，不保存一份重复的业务主数据。所有卡片、图表和列表先应用用户的数据范围，再从采集、任务、识别、异常与复核表聚合。

| 区域 | 展示内容 | 交互与权限 |
| --- | --- | --- |
| 核心指标 | 今日入库文件、排队、识别中、终态成功、终态失败、首次成功率、低置信度、待人工复核 | 显示统计口径、数据范围和更新时间；点击下钻到已过滤列表 |
| OCR 漏斗 | 已入库 → 已提交 → 识别成功 → 自动校验通过 → 待复核 → 已归档 | 各阶段使用文件/候选口径，不用重试调用次数冒充业务量 |
| 趋势分析 | 文件成功/失败量、首次成功率、重试率、平均与 P95 耗时、人工复核率 | 支持日期、部门、采集源、引擎、模型版本、文档类型筛选 |
| 失败分布 | 超时、引擎不可用、文件损坏、不支持格式、低置信度、字段冲突、借贷不平等 | 点击错误码查看任务、调用尝试、原图和异常证据 |
| 我的待办 | 待认领、待复核、待重复审批、逾期任务 | 普通用户仅本人/被分配；领导看部门；管理员看全局并可分派 |
| 最近批次 | 批次号、采集源、文件进度、OCR 进度、异常数、负责人、持续时间 | 可进入批次详情，查看冻结清单、任务和移动状态 |
| 最近失败任务 | 文件、页码、引擎/模型、尝试次数、错误、下次重试时间 | 有权限者可重试、重新识别或转人工；动作需填写原因 |
| 引擎健康 | 启停状态、模型版本、近时段错误率、延迟、最近健康检查 | 仅管理员可查看端点级信息和修改配置；密钥永不回传前端 |
| 通知 | 批次完成、任务分派、审批结果、引擎告警 | 已读/未读、类型过滤，按用户生成回执 |

角色化范围：普通用户查看本人创建、本人负责或明确授权的数据；部门领导查看本部门及下级；管理员查看全局。页面、API、导出和 Agent 查询必须复用同一数据范围组件，不能只在前端隐藏数据。

#### 12.3.2 指标口径

| 指标 | 口径 |
| --- | --- |
| 入库文件数 | `biz_source_file.verify_status=成功` 且入库时间落在筛选区间的文件数 |

| 终态失败 | 达到最大重试、被取消或确认不可处理的逻辑任务；可重试中的失败不计入终态失败 |

### 12.4 OCR 识别处理流程

1. 目录/NAS 采集或网页显式上传产生批次；网页上传传输文件内容，不能提交本机路径让服务端读取。
2. 校验扩展名、文件魔数、大小、页数；ZIP 输入必须防路径穿越、压缩炸弹和超量文件。
3. 文件复制到受控存储，计算并复核 SHA-256 后写 `biz_source_file`，原件此后不可覆盖。
4. 以唯一 `request_id` 创建 `biz_ocr_task`；消费者通过 `status + version` 抢占，避免重复消费。
5. 每次调用引擎向 `biz_ocr_task_attempt` 追加一行；失败按退避策略设置 `next_retry_time`。
6. 成功后按页写 `biz_recognition_page` 新版本，保存分类、固定字段、全文、坐标与原始响应引用，再切换 `current_recognition_version`。
7. 低置信度、借贷不平、字段冲突、未知页或重试耗尽生成 `biz_exception_record` 与 `biz_review_task`。
8. 人工修正只写候选/正式字段、页面关系和变更记录，不修改 OCR 原始证据；通过后进入拆分、重复检验与正式归档。

## 13. OCR 识别全链路专项详细设计（v2.5）

### 13.1 旧功能事实与目标边界

本章以 `D:\Work\PycharmProjects\ImageAnalysis` 当前可运行代码和 `src/config/ht_db.db` 为旧功能依据。Ledgerark 当前 Java 工程没有 OCR Controller、Service、Mapper、调度器、文件存储或前端实现，因此以下内容均为目标设计，不能标记为“已实现”。

| 旧功能 | 实际实现 | Ledgerark 目标处理 |
| --- | --- | --- |
| 未识别文件夹 | `voucherController.identify()` 只读取根目录直接子目录；以目录名后缀排除“凭证信息/识别错误信息/已执行” | 数据库批次为处理真值；稳定检测后冻结清单和指纹，不用目录名代替状态 |
| 图片顺序 | 目录内文件按字符串排序，`1.jpg,10.jpg,2.jpg` 会错序 | 统一自然排序并把顺序写入冻结清单，批次启动后不可改变 |
| 页面分类 | 每页先跑凭证 OCR、再跑发票 OCR；后一次成功会覆盖页面类型 | 分类与字段提取分任务保存；双类型冲突进入复核，不覆盖任何一次响应 |
| 凭证拆分 | 连续凭证页归同组，后续发票/未知页挂当前组；组内最后一张有效凭证页作为主数据 | 规则版本化；保留兼容分组规则，编号冲突只提出边界建议并转人工，支持拆分、合并、重排和改选主页面 |
| 正常凭证 | 以凭证号命名 ZIP，复制到程序目录并写 SQLite | 原文件先不可变入库；候选通过校验后，以候选为事务粒度生成正式档案和版本，包文件只是派生物 |
| 失败凭证 | 随机文件名错误 ZIP，仅存在文件系统；操作员手工选择 ZIP 补录 | 建立失败案件、案件项、异常和复核任务；原图、OCR 证据和人工修改均可追踪 |
| 完成标记 | 未收到 stop 时，即使组内失败或数据库写入失败，也可能把目录改成 `*_已执行` | 每个清单项必须已安全入库，且每个候选已归档或已有持久化失败案件，才允许执行目录处置 |
| 数据更新 | 同凭证号先硬删除旧凭证及发票，再重新插入；ZIP 同名覆盖 | 业务键只用于查重；新采集、新识别和人工修复均新增版本，禁止覆盖历史证据 |

旧程序还存在以下必须在新设计中显式消除的问题：

1. OCR HTTP 固定 30 秒且无重试/退避/熔断，暂停或停止不能中断正在执行的请求；
2. OCR 响应业务状态检查误读了请求参数，无法可靠识别服务端业务失败；
3. 错误补录 UI 与 Worker 的借贷参数顺序相反，可能把借方、贷方互换；
4. 错误 ZIP 使用 0～99999 随机数命名，正常 ZIP 使用凭证号命名，均可能碰撞覆盖；
5. 文件写入、数据库写入和源目录改名不在可补偿的一致性流程内；
6. SQLite 实际只有凭证、发票及四类明细共 6 张表，无批次、页、OCR 尝试、原始响应、异常或复核记录，且无业务索引、唯一约束和启用的外键；
7. `voucher.number` 的实际 SQLite DDL 仍为 `VARCHAR(10)`，当前 ORM 已改为 `VARCHAR(32)`，证明 `create_all()` 不能承担数据库迁移；
8. 错误 ZIP 使用 `extractall()` 直接解压，迁移或新功能必须增加 ZIP 路径穿越、压缩炸弹和超量文件防护。

### 13.2 核心对象与术语

| 对象 | 定义 | 是否业务真值 |
| --- | --- | --- |
| 采集源 | 服务器目录、NAS/共享目录或显式网页上传入口及其扫描策略 | 是，配置真值 |
| 批次 | 一个稳定子文件夹或一次显式上传形成的处理边界 | 是，流程聚合根 |
| 冻结清单项 | 批次启动时观察到的每个文件，即使入库失败也必须有记录 | 是，扫描和对账真值 |
| 原文件 | 复制到受控存储并通过 SHA-256 复核的不可变内容 | 是，证据真值 |
| OCR 逻辑任务/调用尝试 | “需要识别一次”的任务与每次真实引擎调用 | 是，运行证据 |
| 识别页/字段 | 某原文件、页码和识别版本的分类、字段、全文、坐标及原始响应引用 | 是，OCR 原始结论，不允许人工覆盖 |
| 拆分运行 | 对某批次的一次完整分组算法执行，保存规则版本和输入识别版本快照 | 是，算法版本证据 |
| 候选凭证 | 自动拆分后、正式归档前可复核的凭证及其页面集合 | 是，业务草稿 |
| 原子异常 | 某页、任务、字段或候选的一条具体问题事实 | 是，问题证据 |
| 失败案件 | 把同一失败凭证的多页、任务、异常和处理上下文聚合成一个待办对象 | 是，失败处理真值 |
| 复核任务 | 谁负责、何时处理以及处理结果的人工作业 | 是，人员流程真值 |
| 正式档案/档案版本 | 通过归档门禁后的凭证、发票、分录、页面关系和版本快照 | 是，正式业务真值 |
| ZIP/预览图 | 根据不可变原件和档案版本生成的下载或预览产物 | 否，可重建派生物 |

“失败凭证集中归档”在产品和数据模型中统一称为**失败凭证暂存/待处理中心**：它负责安全保存证据和处理上下文，但不创建残缺的正式 `biz_archive`。失败修复后仍必须通过自动校验、重复审批和正式归档门禁。

### 13.3 八阶段端到端流程

| 阶段 | 核心动作 | 主要输出 | 失败去向 |
| --- | --- | --- | --- |
| 1. 发现未识别文件夹 | 扫描采集源、稳定检测、目录指纹、批次租约 | 批次、冻结清单 | 采集源/目录异常 |
| 2. 文件安全入库 | 魔数、大小、页数、安全校验；复制、SHA-256 复核 | 不可变原文件 | 入库异常或不支持文件 |
| 3. OCR 与字段提取 | 预处理、逻辑任务、调用尝试、分类、字段和原始响应 | 版本化识别页/字段 | 技术失败自动重试，耗尽后失败案件 |
| 4. 凭证拆分与自动校验 | 按冻结顺序分组，生成候选；校验必填、期间、借贷和页面边界 | 候选、候选页、校验结果 | 边界/字段/业务异常进入失败中心 |
| 5. 重复检测与审批 | 文件哈希、图像/OCR 相似度、业务键证据 | 重复案件或可归档门禁 | 待人工确认/审批 |
| 6. 成功凭证原子归档 | 候选级事务生成档案、凭证、分录、发票、版本和文件关系 | 正式档案及 outbox 事件 | 归档异常，可恢复重试 |
| 7. 失败凭证集中待处理 | 聚合失败案件，认领、补录、重识别、重拆分或关闭 | 失败案件、复核任务、修复版本 | 保持待办或不可处理关闭 |
| 8. 批次收尾与目录处置 | 对账全部清单项，成功/失败分流目录，刷新指标和通知 | 完成/部分失败批次 | 目录处置异常独立重试 |

批次允许部分候选成功、部分候选失败。一个失败候选不能回滚同批次已完成的正式档案；批次状态只是汇总，原文件、任务、候选和失败案件明细才是事实来源。

### 13.4 第一步：发现未识别文件夹与冻结批次

#### 13.4.1 扫描规则

1. 调度器只扫描 `biz_collection_source` 配置的根目录，不接受浏览器提交任意本机路径；
2. 默认只读取直接子目录，与旧功能保持一致；是否递归必须作为采集源显式配置；
3. 使用规范化绝对路径并校验仍位于配置根目录下，拒绝符号链接、Windows 重解析点或越界路径；
4. 排除成功目录、失败待处理目录、临时目录、隐藏目录和正在上传目录，排除规则保存到采集源配置；
5. 同一子目录连续两次观察到文件数量、相对路径、大小和修改时间都不变，且超过 `stable_wait_sec`，才允许冻结；
6. 文件使用自然排序，排序键和结果写入 `biz_batch_file_item.natural_order`；
7. 冻结后新增或修改文件不静默并入当前批次，生成 `FOLDER_CHANGED_AFTER_FREEZE` 异常，并按策略创建新批次或等待人工确认。

#### 13.4.2 批次幂等与租约

- `folder_fingerprint = SHA-256(source_id + canonical_relative_folder + frozen_manifest_hash)`；唯一键 `(source_id, folder_fingerprint)`；
- 扫描采集源使用 `lease_owner + lease_until + version` 条件更新抢占，服务崩溃后租约自动过期；
- 建批和清单冻结使用短事务，文件系统遍历不持有数据库长事务；
- 同一目录重复扫描命中已有批次时返回原批次，不生成重复任务；目录内容改变后形成新指纹和新批次；
- 空目录和无支持文件目录也形成可审计结果，可标记 `IGNORED_EMPTY`，避免旧版反复扫描。

### 13.5 第二步：文件入库、OCR 与识别版本

#### 13.5.1 文件安全入库

每个冻结清单项独立处理：校验扩展名与文件魔数、大小、页数、图片尺寸和可读性；ZIP/PDF/TIFF 还需限制解压后条目数、总大小、压缩比和最大页数。文件先复制到临时存储键，计算源端与目标端 SHA-256，复读一致后原子切换为正式存储键并写 `verify_status=成功`。

原件成功入库后不可原位覆盖或以凭证号命名。存储键使用批次 ID、原文件 ID、ULID 或内容摘要组合；凭证号只作为显示和检索字段。多页 PDF/TIFF 的稳定页身份使用 `(source_file_id, page_no)`，页面渲染参数随 OCR 配置快照保存。

#### 13.5.2 OCR 编排

1. 为每页创建 `PAGE_CLASSIFY` 逻辑任务；根据策略创建 `VOUCHER_EXTRACT`、`INVOICE_EXTRACT`、`FULLTEXT` 等子任务；
2. Worker 通过状态、优先级、`next_retry_time`、租约和乐观锁抢占任务；引擎调用在事务外执行；
3. 每次真实调用先创建 `biz_ocr_task_attempt`，完成后写终态、耗时、错误码、引擎请求号和请求/响应引用；
4. 超时、连接失败、限流和临时服务错误按指数退避重试；文件损坏、不支持格式和业务字段异常不做无意义自动重试；
5. 同一页的凭证、发票解析器均成功时保存两个候选结论并产生 `DUAL_TYPE_CONFLICT`，不得用后执行的结果覆盖先执行结果；
6. 一次完整重识别使用新的 `recognition_version`；全部页成功落库后，事务内切换 `biz_source_file.current_recognition_version`；旧版本只读保留。

识别原始响应建议保存到受控对象存储，数据库只存内容摘要、受控引用和必要索引字段。日志禁止输出完整票面、税号、银行账号、OCR 原文或服务密钥。

### 13.6 第二步续：凭证拆分、字段提取与自动校验

#### 13.6.1 兼容且可复核的分组算法

```text
current = null
for page in frozen_pages_by_natural_order:
    if page.type == VOUCHER_HOME:
        if current is null:
            current = start_candidate(page)
        elif previous_page.type in {INVOICE, ATTACHMENT, UNKNOWN}:
            close(current); current = start_candidate(page)
        elif same_normalized_voucher_key(current, page) or page.key_missing:
            append(current, page)
        else:
            append(current, page)
            raise BOUNDARY_UNCERTAIN / VOUCHER_NO_CONFLICT
    elif page.type in {INVOICE, ATTACHMENT, UNKNOWN}:
        if current is not null:
            append(current, page)
        else:
            create_orphan_failure_case(page)
close(current)
```

连续凭证页仍先保守归入同一候选，以兼容旧功能的多页凭证；若高置信凭证号变化，只生成“建议边界”和人工复核任务，不直接丢页或覆盖主数据。采集源可在真实样本验证后启用“高置信编号变化自动切分”，但规则版本、阈值和输入识别版本必须保存到 `biz_voucher_split_run`。

候选主页面默认取最后一张有效凭证页；人工可改选。人工拆分、合并、页面重排、页面排除或字段补录必须增加候选版本和修订快照，OCR 原始页与原始字段不修改。

#### 13.6.2 自动校验门禁

| 规则 | 阻断条件 | 处理 |
| --- | --- | --- |
| 必填字段 | 凭证类型、年度、期间、凭证号缺失 | 失败案件，允许补录或重识别 |
| 日期/期间 | 日期非法、超账套期间或年月不一致 | 失败案件或部门复核 |
| 借贷平衡 | `abs(debit-credit)` 超过配置容差 | 阻断归档，人工确认不得无理由绕过 |
| 分录合计 | 分录借贷合计与凭证头不一致 | 阻断归档并定位具体分录 |
| 页面边界 | 首张孤立发票、未知首页、凭证号冲突或页面重复归组 | 进入拆分复核 |
| 置信度 | 页面类型或关键字段低于任务保存的阈值快照 | 进入字段复核 |
| 重复检测 | SHA-256、感知哈希、OCR 相似度或业务键命中 | 创建重复案件，不能直接覆盖或数据库拒绝 |
| 原件完整性 | 任一清单项未安全入库、哈希不一致或页面缺失 | 批次与候选均不能归档 |

每条规则结果写入 `biz_candidate_validation`，包含候选版本、规则码、严重级别、期望值、实际值和证据。候选只有在所有阻断规则通过且没有活动重复审批时，才能进入 `READY_TO_ARCHIVE`。

### 13.7 第三步：凭证文件与凭证信息归档

正式归档以**单个候选凭证**为最小事务，不以整个文件夹为一个大事务。归档接口必须携带 `requestId`、候选 `version` 和操作原因。

事务内完成：

1. 锁定候选并再次校验状态、候选版本、活动异常和重复案件；
2. 创建或幂等取得 `biz_archive`，其中 `source_candidate_id` 唯一；
3. 创建 `biz_voucher`、`biz_voucher_entry`、`biz_invoice`、发票明细/运输扩展；
4. 创建 `biz_archive_version` 完整快照及 `biz_archive_file_relation` 页面关系；
5. 更新档案当前版本和候选状态，追加 `biz_workflow_history`；
6. 同事务写 `biz_outbox_event`，用于派生 ZIP、全文索引、指标和通知。

ZIP 不是正式档案的唯一载体。派生包先写临时对象、校验条目清单和 SHA-256 后再激活；生成失败只影响下载产物状态，不回滚已提交的业务档案。相同凭证号或发票号码再次采集时完整保留，进入重复案件；不得像旧系统一样硬删除旧记录或覆盖同名 ZIP。

### 13.8 第四步：失败凭证集中暂存与待处理

#### 13.8.1 失败案件形成

下列情况创建或合并到一个活动 `biz_ocr_failure_case`：文件入库失败、OCR 重试耗尽、双类型冲突、无法拆分、孤立发票/未知页、关键字段缺失、借贷不平、疑似重复待审批、归档事务失败、派生包失败或源目录处置失败。`biz_exception_record` 保存原子问题，失败案件保存“这一份失败凭证”的聚合快照，`biz_review_task` 只负责人工作流，三者职责不得混用。

每个失败案件通过 `biz_ocr_failure_item` 关联多张原文件、页、OCR 任务、识别版本、候选和异常。错误 ZIP 可作为导出或迁移兼容产物，但随机 ZIP 文件名不再是案件主键，也不能替代数据库台账。

#### 13.8.2 人工处理动作

| 动作 | 结果 |
| --- | --- |
| 认领/分派 | 校验用户状态、部门数据范围、任务能力和乐观锁 |
| 重试 OCR | 新增逻辑任务或调用尝试，保留旧失败证据 |
| 重新识别 | 新增 `recognition_version`，成功后重新拆分和校验 |
| 改分类/调边界 | 新增拆分运行或候选修订，不修改原始 OCR 页 |
| 补录/修正字段 | 写候选修订及字段前后值、原因、操作者，不修改识别字段原值 |
| 合并/拆分候选 | 锁定批次和相关候选；旧候选标记被替代，页面不删除 |
| 确认非业务文件 | 逻辑排除并保留原件、原因和审计 |
| 修复并归档 | 重新执行校验门禁和候选级归档事务，回写 `resolved_archive_id` |
| 不可处理关闭 | 需权限、原因和证据；只关闭案件，不删除原图和 OCR 响应 |

失败案件状态为：`0-待分派`、`10-待认领`、`20-处理中`、`30-等待重试`、`40-已修复归档`、`50-人工完成`、`60-忽略关闭`、`90-不可处理关闭`。一个目标、失败阶段和错误类型同时只能存在一个活动案件，使用生成列活动键和唯一索引控制。

### 13.9 第五步及后续：批次收尾、目录处置与对账

批次出箱条件：所有冻结清单项均已安全入库或形成不可处理异常；每张页已归属候选、失败案件或明确逻辑排除；每个候选已正式归档、进入活动失败案件或完成重复审批分支。

- 全部成功：移动到 `已处理/YYYY/MM/DD/{batchNo}_{originalFolderName}`；
- 部分或全部失败：移动到 `失败待处理/YYYY/MM/DD/{batchNo}_{originalFolderName}`；
- 同盘优先原子改名；跨盘使用“复制 → 目标清单和哈希复核 → 删除源”的补偿流程；
- 每次处置写 `biz_batch_disposition`，失败按租约和退避重试，不回滚已归档凭证；
- 原目录名必须作为元数据保留，不能像旧系统一样只留下时间戳；
- 定时对账任务从明细重算批次计数、发现超时租约、孤立存储对象、缺失 outbox、档案版本指针漂移和长期未处理案件。

#### 13.11.2 错误码

错误对象统一包含 `failure_stage`、`error_code`、`retryable`、脱敏 `message`、`evidence_ref` 和 `trace_id`。

| 阶段 | 代表错误码 | 默认处理 |

### 13.12 详细表结构设计

#### 13.12.1 公共约定

- 目标数据库为 MySQL 8；主键统一 `BIGINT`，金额统一 `DECIMAL(18,2)`，置信度统一 `DECIMAL(6,5)`，时间统一 `DATETIME(3)`；
- 可修改业务表包含 `version INT NOT NULL DEFAULT 0`、`create_by/create_time/update_by/update_time`；追加证据表只保留创建信息，不使用 `del_flag`；
- 原文件、OCR 响应、识别结果、拆分运行、候选修订、失败证据、档案版本和流程历史禁止级联删除；
- 存储表只保存受控 `storage_key/payload_ref`，不保存公开 URL、明文密钥或浏览器本机路径；
- 业务键用于检索和重复案件，不做阻止留存的无条件唯一约束；

### 13.13 事务、幂等、租约与最终一致

| 操作 | 事务边界 | 幂等/一致性控制 |
| --- | --- | --- |
| 文件夹发现 | 文件扫描事务外；建批和冻结清单短事务 | 目录路径+指纹唯一；采集源租约 |
| 文件入库 | 复制/哈希事务外；清单项和原文件状态短事务 | 临时键→哈希复核→正式键；清单路径唯一 |
| OCR 调用 | 条件抢任务短事务；HTTP 事务外；结果短事务 | requestId、任务版本、尝试序号唯一；租约过期恢复 |
| OCR 版本激活 | 识别页/字段、任务成功、当前版本指针、outbox 同事务 | 文件+版本+页码唯一，重复消息返回已有结果 |
| 自动拆分 | 拆分运行、候选、候选页、校验和异常同事务 | 批次+运行版本唯一；运行内页面唯一归属 |
| 失败捕获 | 原子异常、失败案件、案件项和活动复核任务同事务 | 活动异常/案件/任务生成键唯一 |
| 正式归档 | 锁候选；档案、凭证、分录、发票、版本、页面关系和 outbox 同事务 | `source_candidate_id`、archive requestId 唯一 |
| ZIP/索引/通知 | 事务提交后由 outbox Worker 执行 | 事件聚合键唯一；失败退避重试 |
| 目录移动 | 文件系统事务外；每次处置短事务 | `biz_batch_disposition` 租约、清单哈希和补偿 |

系统按“至少一次执行 + 唯一键 + 状态条件更新”设计，不假定调度或消息只执行一次。任何业务删除都不能级联清除原文件、OCR 尝试、识别页、失败证据、档案版本或流程历史。

#### 13.14.2 失败 ZIP 与已执行目录

错误 ZIP、无数据库记录的 `*_已执行` 目录和字段解析失败记录不得直接生成正式档案。它们导入专用 legacy 批次，建立原文件、`LEGACY_OCR_FAILED/LEGACY_UNCLASSIFIED` 异常、失败案件和复核任务。`*_已执行` 只表示旧程序尝试过，不代表成功；只有数据库记录、有效附件和字段校验全部通过，才可标记历史已归档。

迁移先冻结 SQLite 和所有候选根目录，计算数据库 SHA-256、文件清单、ZIP test、条目数和文件 SHA-256。建议增加：

- `biz_legacy_import_run(run_no, source_db_hash, source_root, status, counters_json, started_time, finished_time, error_msg)`；
- `biz_legacy_id_map(source_system, source_db_hash, source_table, legacy_id, target_table, target_id, row_hash, status, error_msg)`，唯一 `(source_db_hash,source_table,legacy_id)`。

迁移必须可重跑并输出行数、父子关系、字段转换错误、缺失/孤儿文件、ZIP 条目、哈希和抽样下载报告；旧库与旧附件切换后只读保留。

### 13.15 验收场景与运行指标

#### 13.15.1 核心验收用例

1. 不稳定目录不建批；稳定后重复扫描十次只生成一个批次；
2. `1.jpg、2.jpg、10.jpg` 和多页 PDF 的顺序正确，冻结后新增文件不进入当前批次；
3. 不同目录即使内容相同也分别留存；同目录相同指纹不重复建批；
4. 扩展名与文件魔数不一致时停止 OCR、保留清单项并生成异常；
5. OCR 超时按退避策略重试，每次调用均有独立尝试记录；
6. Worker 崩溃后租约到期可恢复，不产生重复任务或重复当前识别页；
7. 一页同时命中凭证和发票时生成分类冲突，不出现后调用覆盖；
8. `V001、V002、V001、发票` 生成一个冲突候选；
9. `V001、发票、V002、附件` 生成两个候选；
10. `发票、未知、V001` 生成一个孤立失败案件和一个正常候选，所有页面恰好归属一次；
11. 多页 PDF 的多个页可进入同一候选，不受文件级唯一约束阻挡；
12. 低置信度、凭证号缺失或借贷不平时不得自动归档，只生成一个活动失败案件和复核任务；
13. 重复提交归档请求只生成一个档案；再次采集同号凭证不删除旧档案；
14. 一个批次部分成功、部分失败时，成功候选正常归档，失败候选全部进入待处理中心；
15. 人工修正、重拆分和重识别后，原 OCR、旧拆分运行和旧候选版本仍可追溯；
16. ZIP 路径穿越、压缩炸弹、越界路径和符号链接均被拒绝并审计；
17. 源目录移动失败不会回滚档案，重试成功后处置流水完整；
18. 正式档案可反查候选、拆分运行、识别页、引擎尝试、原文件、冻结清单和来源目录。

#### 13.15.2 运行指标

除 §12.3 的文件成功率、首次成功率、重试率和 P95 外，新增：稳定目录等待时长、单文件入库失败率、分类冲突率、孤立页率、自动拆分通过率、借贷不平率、失败案件新增/关闭/积压/逾期、平均人工处理时长、候选自动归档率、派生包失败率、目录处置失败率和对账差异数。所有指标必须带时间范围、部门/采集源/引擎/模型/规则版本及数据截止时间。
