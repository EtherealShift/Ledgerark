## 1. 系统定位与目标

面向企业财务档案场景的**电子档案管理系统**，管理对象为记账凭证、发票等票据影像及其结构化识别数据：

- **收**：后端按“一个子文件夹一个扫描批次”采集凭证/发票图片，安全入库后由 OCR 自动识别和拆分；
- **管**：分类、组卷（归档）、保管期限、密级管理；
- **查**：组合条件 + 全文检索，快速定位档案与票据；
- **用**：借阅申请、审批、归还、逾期提醒；
- **销**：到期销毁，审批 + 监销留痕。

**建设目标**：数据规范化（MySQL 8.0）、全流程留痕（审计日志）、权限可控（RBAC + 密级）、识别引擎可扩展、与现有骨架无缝衔接。

## 2. 骨架现状盘点（ledgerark）

### 2.1 模块结构（Maven 多模块）

```
ledgerark（父 POM：org.ledgerark:ledgerark:0.0.1）
├── ledgerark-admin      # 启动模块：@SpringBootApplication(scanBasePackages="org.ledgerark")、@MapperScan
│                        #    Web 入口 + Controller（web.controller.system）
├── ledgerark-common     # 公共模块（纯公共，不依赖业务）：Result / PageQuery / LoginUser、
│                        #    BaseEntity / ResultCode / BaseException
├── ledgerark-framework  # 框架模块：Sa-Token 拦截器、BCrypt 密码编码器、MyBatis-Plus 分页配置、
│                        #    全局异常处理（含 Sa-Token 异常）、登录服务（SysLoginService）、UserUtils
├── ledgerark-system     # 业务模块：Service / Mapper / DTO / VO + 业务实体（entity.sys）、

└── sql                  # 数据库脚本（sys_user.sql / sys_role.sql / sys_user_role.sql 完整建表）
```

依赖链：`admin → framework → system → common`（admin 只依赖 framework）。

**分层职责（沿用骨架现状）**：
- `ledgerark-common`：不依赖业务，纯公共（Result/BaseEntity/PageQuery/LoginUser/ResultCode/BaseException）；
- `ledgerark-framework`：横切能力（鉴权、异常、配置、工具、后续 AOP/文件/任务）；
- `ledgerark-system`：业务服务与持久层（Service/Mapper/DTO/VO）+ 业务实体/枚举/常量/异常；
- `ledgerark-admin`：Web 装配层（启动类、Controller、配置资源）。

## 5. 数据库设计（v2.3 目标模型）

### 5.1 设计边界与实现状态

数据库以 MySQL 8.0 为事务数据源，MyBatis-Plus 负责持久化与分页，Sa-Token 会话中的用户 ID 作为审计操作者。数据库只保存文件元数据、业务数据、OCR 结果与审计记录；图片原文件存放在受控文件系统或对象存储中，数据库通过 `storage_key` 引用，浏览器端不直接访问服务器物理路径。

本节使用以下状态标识，避免将设计稿误认为已实现功能：

| 标识 | 含义 |
| --- | --- |
| ✅ | 仓库已有实体与 DDL，当前骨架正在使用 |
| 🟡 | 仓库已有 DDL，但对应业务服务尚未完成 |
| 🆕 | v2.3 目标模型，当前仓库尚无正式 DDL/实体，需要新增迁移脚本 |

| 数据域 | 当前基线 | v2.3 补充重点 |
| --- | --- | --- |
| 用户权限 | `sys_user`、`sys_role`、`sys_user_role` ✅ | 部门领导角色、角色数据范围、登录日志、Agent 审计 🆕 |
| 系统管理 | `sys_dept`、`sys_menu`、`sys_role_menu`、字典、操作日志 🟡 | 通知、用户通知、Agent 会话与引用记录 🆕 |
| 旧档案模型 | `biz_archive.sql` 中 11 张业务表 🟡 | 保留为迁移基线，不直接承担扫描拆分全过程 |
| 采集识别 | 仅 `biz_archive_file`、`biz_ocr_task` 🟡 | 采集源、扫描批次、不可变原文件、逐页 OCR 版本 🆕 |
| 拆分复核 | 无 | 凭证候选、页面编排、异常、人工复核任务 🆕 |
| 重复检验 | 仅文件 SHA-256 字段 | 重复案件、证据项、审批结论，重复数据不删除 🆕 |
| 正式档案 | 档案、凭证、发票、明细 🟡 | 当前版本、修改记录、流程历史、原文件关联 🆕 |
| Agent 检索 | 无 | 检索文档、分块、查询日志、档案引用及权限快照 🆕 |

### 5.2 命名、类型与通用字段规范

| 规则 | 约定 |
| --- | --- |
| 表前缀 | `sys_` 表示用户、权限、组织、日志与通知；`biz_` 表示采集、识别、档案及业务流程 |
| 主键 | `id BIGINT`，默认自增；Java 使用 `Long`，不在前端以浮点数处理，接口建议序列化为字符串 |
| 字符集 | `utf8mb4`，排序规则统一 `utf8mb4_unicode_ci` |
| 金额 | `DECIMAL(18,2)`；禁止使用 `FLOAT/DOUBLE` 保存金额 |
| 时间 | 新流水表采用 `DATETIME(3)`；Java 对应 `LocalDateTime`，业务日期采用 `DATE` |
| 状态 | `TINYINT` + Java 枚举；合法流转由 Service 层状态机校验，不依赖 MySQL `CHECK` 作为唯一保障 |
| JSON | OCR 原值、拆分计划、重复证据快照、版本快照采用 MySQL `JSON`；MyBatis-Plus 实体使用 JSON TypeHandler 或先映射为 `String` |
| 审计字段 | 可变业务实体继承 `BaseEntity`：`create_by/update_by/create_time/update_time/remark` |
| 逻辑删除 | 仅允许删除的可变实体增加 `del_flag` 并使用 `@TableLogic`；原文件、OCR 版本、流程历史、登录/操作/Agent 日志不做逻辑删除 |
| 乐观锁 | 人工复核任务、重复案件、档案主表等并发修改对象增加 `version INT`，实体使用 MyBatis-Plus `@Version` |
| 外键策略 | 核心数据默认 `RESTRICT`；仅纯关联表可 `CASCADE`。生产环境如因批量迁移关闭物理外键，仍须保留相同索引与 Service 层引用校验 |

`del_flag` 只表达“业务界面不可见”，不能用于抹除审计证据。已经归档的文件与版本必须通过作废、销毁等受控状态流转处理。

### 5.3 系统、角色与数据权限表

#### 5.3.1 现有核心表

### 5.8 正式档案、发票、附件与版本

#### 5.8.1 档案聚合模型

`biz_archive` 是正式档案聚合根：一个凭证档案对应一条 `biz_archive` 和一条 `biz_voucher`，可关联多条 `biz_invoice` 与任意附件；独立发票档案可没有 `biz_voucher`。借阅、销毁等旧功能继续引用 `biz_archive.id`。

| 表 | 核心字段与约束 | 说明 |

MySQL 仍是档案事实来源。第一阶段先使用结构化条件查询和 MySQL 8 `ngram` 全文检索，不在当前库中强行保存向量字段。

| `biz_search_chunk` 🆕 | document_id, chunk_no, chunk_text, metadata_json, token_count, embedding_model, embedding_ref | 为 Agent 提供带档案引用的分块；语义检索启用后 `embedding_ref` 指向外部向量索引 |

### 5.11 状态编码建议

状态码应落入系统字典，并在 Java 中建立同名枚举。数据库保存数值，API 输出数值与可读标签。

**批次 `biz_collection_batch.status`**：`0-待采集`、`10-文件入库`、`20-识别中`、`30-自动拆分`、`40-待人工复核`、`50-重复检验`、`60-已完成`；异常态 `91-部分失败`、`92-识别失败`、`93-已取消`、`94-源目录移动失败`。

**候选 `biz_voucher_candidate.status`**：`0-待识别`、`10-待拆分确认`、`20-待复核`、`30-待重复审批`、`40-已归档`；异常态 `91-识别异常`、`92-已驳回`、`93-确认重复`、`94-已作废`。

**重复案件 `biz_duplicate_case.status`**：`0-待分析`、`10-待人工确认`、`20-待审批`、`30-已结案`、`90-已取消`。

### 5.12 索引、幂等与约束策略

1. **批次幂等**：`(source_id, folder_fingerprint)` 唯一；同一文件夹被重新投放且内容变化时指纹变化，生成新批次并保留关联说明。
2. **原文件幂等**：`(batch_id, relative_path)` 唯一；SHA-256 仅建普通索引，重复文件也允许写入。
3. **OCR 版本幂等**：`(source_file_id, recognition_version)` 唯一；任务号、请求号分别唯一，防止消息重投产生双份结果。
4. **拆分顺序**：`(candidate_id, page_order)` 唯一；`natural_order` 在批次开始后不可变。
5. **凭证业务键**：只建组合索引，不建唯一键；否则会违背“相同凭证号再次采集仍须保留并审批”的业务规则。
6. **发票号码**：同样不做无条件唯一；以 `invoice_code + invoice_no + 销方税号 + 金额 + 图像/OCR 相似度` 形成重复证据。
7. **版本唯一**：`(archive_id, version_no)` 唯一，`biz_archive.current_version_id` 指向当前版本；切换版本在事务中完成。
8. **工作台查询**：批次、复核任务、重复案件均建立 `(status, dept_id, create_time)` 或等价联合索引，列顺序以实际 SQL 过滤条件为准。
9. **大日志表**：登录、操作、Agent 查询与流程历史按时间建立索引；数据量达到千万级后再评估按月分区/冷热归档，避免初期过度设计。

### 5.13 事务、并发与文件一致性

- **采集事务**：创建批次、写入文件清单和 `biz_source_file` 元数据按批次短事务提交；文件复制成功并经 SHA-256 复核后才标记 `verify_status=成功`。
- **拆分事务**：候选、候选页面及异常记录一次性写入；失败时不改变批次的已冻结清单，可安全重跑并生成新的规则版本。
- **人工复核事务**：校验 `version` → 更新候选/任务 → 追加流程历史与变更记录，任一步失败全部回滚。
- **重复审批事务**：锁定重复案件 → 写结论 → 更新候选与档案关系 → 追加审批/流程流水；不执行文件删除。
- **归档事务**：创建 `biz_archive`、凭证/发票、档案版本、文件关联和检索待建标记；事务提交后再异步构建全文索引。
- **源目录移动**：确认所有文件已安全入库且批次业务处理完成后，移动至 `已处理/YYYY/MM/DD/{batchId}_{originalFolderName}`。目录移动属于数据库外部副作用，不与数据库事务强绑；失败写入批次移动状态和异常记录，由任务重试。
- **审计操作者**：从 Sa-Token Session 获取当前用户，写入 `create_by/update_by/operator_id`；异步任务使用明确的系统账号或 `operator_type=SYSTEM`，不得伪装成人工用户。

## 6. 核心流程设计（含代码落点）

### 6.1 归档流程

```
发现子文件夹 ─▶ 创建扫描批次并冻结自然排序 ─▶ 原文件安全入库/哈希复核
      └──────────────────────────────▶ 逐页 OCR（保留识别版本）
                                           ▼
                                    自动页面分类与凭证候选拆分
                                           ▼
                              字段冲突/未知页面/借贷不平人工复核
                                           ▼
                    业务键 + 图像/OCR 相似度重复检验与人工审批
                                           ▼
             建立正式档案、版本、文件关联及检索文档 ─▶ 批次完成
                                           ▼
                  原目录移入已处理目录（失败单独重试，不回滚档案）
```

拆分边界示例：`凭证001、凭证002、凭证001、发票` 归为**一个候选**并标记凭证号冲突；`凭证001、发票、凭证002、附件` 归为两个候选。事务边界详见 §5.13。

### 6.2 借阅流程（状态机 + 审批）

```
借阅申请（BorrowService.apply）→ 待审批
    → 同意：biz_archive 状态→已借出（borrow_status=1），借单→已批准
    → 驳回：借单→已驳回，档案不变
已借出 → 归还登记（BorrowService.return）：借单→已归还，borrow_status 复位
超期 → 定时任务置"逾期" + 通知，归还后仍归"已归还"
```

### 6.3 销毁流程（双审批留痕）

```
到期预警清单 → 销毁申请（DestructionService.apply，仅已归档且未借出）
    → 审批（DestructionService.approve，biz_approval_record 留痕）
    → 批准：登记销毁方式/时间/监销人 → 物理删除文件 → 档案状态→已销毁
    → 驳回：申请作废，档案保持已归档
```

### 6.4 OCR 识别流程（异步解耦）

```
提交任务（排队）→ 消费者以 version 乐观锁抢占（防重复消费）
    → 调用识别引擎 → 成功：追加 biz_recognition_page 识别版本并切换当前版本
    → 失败：记录 error_msg、retry_count 与 next_retry_time 后自动重试
    → 超时/重试耗尽：生成 biz_exception_record + biz_review_task，转人工介入
```

## 7. 权限模型设计（基于骨架现状）

- **已落地**：`sys_user`（当前 `user_type` 仍为 1 管理员 / 2 普通用户）+ `sys_user_role` + Sa-Token 登录校验（白名单 `/sys/login/doLogin`、`/sys/login/register`）+ 登录返回 token + Session 中保存 `LoginUser` + 统一鉴权异常处理。
- **规划**：
  1. 内置角色固定为 `ADMIN`（管理员）、`DEPT_LEADER`（部门领导）、`USER`（普通用户）；注册默认授予 `USER`，部门领导由管理员分配，不再扩展 `user_type` 枚举承载新角色；
  2. 菜单/权限点：`sys_menu`（菜单树 + `perms` 权限码 `模块:功能:操作`），角色-菜单关联 `sys_role_menu`；
  3. 接口级鉴权：`@SaCheckPermission("archive:review:approve")` 等权限注解 + Sa-Token 统一异常处理；
  4. 数据权限：`sys_role.data_scope + sys_role_dept`，MyBatis-Plus 数据权限拦截器根据核算主体、部门、负责人和密级追加条件；管理员看全部，部门领导看本部门及下级，普通用户看本人/被授权数据；
  5. 审计：用户启停用、重置密码、角色调整、复核、重复审批和 Agent 查询必须写入登录/操作/流程/Agent 审计表，密码与 token 永不写日志。

### 8.2 编码约定（对齐骨架）

- 实体：`@Data @TableName("biz_xxx")` 继承 `BaseEntity`；**需要逻辑删除的表加 `delFlag` 字段 + `@TableLogic`**（全局 `logic-delete-field: delFlag` 已配置，无需软删的表不加）；
- 并发：复核任务、重复案件、批次和档案实体的 `version` 字段使用 `@Version`；更新结果为 0 时返回“数据已被他人更新”，禁止静默覆盖；
- JSON：显式配置 `autoResultMap = true` 与 JSON TypeHandler，或先以 `String` 保存；不得依赖隐式对象序列化；
- 响应：一律 `Result<T>`；业务异常放 `system.exception`（已有 `UserException`，新增模块可建 `ArchiveException extends BaseException`）；
- 命名：接口 `I{Module}Service`、实现 `{Module}ServiceImpl`（沿用骨架 `ISysUserServiceImpl` 风格）；
- 入参/出参：DTO（含 jakarta validation 注解）/ VO（`@Builder`），禁止直接暴露实体；
- 分页：`PageQuery` + MyBatis-Plus `Page`，页大小上限 100（骨架已统一）；
- 权限：Controller 方法上加权限注解（规划）；当前用户取 `UserUtils.getCurrentUser()`。

## 9. 关键设计思路与决策

| # | 设计点 | 决策与理由（含骨架适配） |
| --- | --- | --- |
| ① | 子文件夹即批次 | `biz_collection_batch` 固化文件夹指纹和自然排序；启动后不再悄悄吸收新增文件，保证识别结果可重放 |
| ② | 原始数据不可变 | 原图片、SHA-256、OCR 历史版本只追加不覆盖；人工操作调整关联、主页面和档案版本，不删除证据 |
| ③ | 连续凭证页分组 | 遇到凭证页先继续归入当前候选，只有经过发票/附件区后出现的新凭证页才开始下一候选；默认最后凭证页为主数据页 |
| ④ | 凭证号冲突转人工 | `001 → 002 → 001` 仍是一个候选，记录冲突和复核原因，不按 OCR 号码强行拆成三份 |
| ⑤ | 重复数据先留后审 | SHA-256、感知哈希、OCR/版面相似度和业务键共同形成证据；凭证号与发票号不做会阻止入库的唯一约束 |
| ⑥ | 候选与正式档案隔离 | 自动拆分先落候选层，复核和重复审批通过后才生成 `biz_archive`，避免低置信 OCR 污染正式数据 |
| ⑦ | 档案聚合与版本 | 一个凭证档案对应一个档案根和零或一个凭证，可含多张发票/附件；每次修改生成档案版本和字段级变更记录 |
| ⑧ | OCR 双轨制 | 引擎原始 JSON、逐页结构化字段与人工校正后的正式字段并存，既可追溯又便于统计计算 |
| ⑨ | 状态机 + 流程历史 | 当前状态保存在业务表，所有流转追加到 `biz_workflow_history`；Service 层校验合法流转 |
| ⑩ | 逻辑删除与销毁分离 | `del_flag` 只用于允许软删的实体；审计、原文件、识别版本不软删，物理销毁必须经过审批并留下台账 |
| ⑪ | 数据范围前置 | 核算主体、账套、部门、负责人落在聚合根/批次；MyBatis-Plus 在查询层过滤，Agent 检索同样先鉴权再召回 |
| ⑫ | Agent 可引用、可审计 | 每次查询保存权限快照、模型、耗时、回答摘要和引用档案；第一阶段只读，回答必须带内部资源引用 |
| ⑬ | 全文检索分层 | 先以 MySQL 8 `ngram` + 结构化索引完成一期；语义检索后续接外部向量索引，MySQL 只保存 `embedding_ref` |
| ⑭ | 文件与数据库最终一致 | 源目录移动是事务外副作用；归档先提交，移动失败记录状态并重试，不能因移动失败回滚已校验数据 |
| ⑮ | 并发控制 | 批次、复核任务、重复案件、档案使用 `@Version` 乐观锁；调度任务以唯一请求号和状态抢占实现幂等 |
| ⑯ | 骨架适配 | 继续复用 Java 21、Spring Boot 4.1、MyBatis-Plus、Sa-Token、BCrypt、`Result<T>` 与统一异常体系 |

## 11. 风险与注意事项

1. `sql/biz_archive.sql` 是旧档案模型基线，不能在已有数据的共享环境中直接重跑，也不能在未调整唯一约束前承接“重复但保留”的新规则。
2. 目录扫描只能由有权限访问服务器/NAS/共享目录的后端进程完成；Web 页面只能配置采集源、查看状态和发起重试。
3. 原文件入库必须先复制、计算并复核 SHA-256，再允许移动源目录；跨磁盘移动应按“复制 → 校验 → 删除源”的补偿流程实现。
4. OCR 置信度不足时不得自动归档；页面分类、凭证号冲突、借贷不平和疑似重复均应生成可追踪的异常/复核任务。
5. `voucher_no`、`invoice_code + invoice_no` 不得设置阻止重复记录写入的唯一约束；重复控制由案件与审批流程承担。
6. Agent 查询必须复用与普通检索相同的数据范围，日志不得记录密码、token、完整身份证号或未脱敏银行卡号；引用记录必须能追溯到档案版本。
7. MyBatis-Plus 的 `@TableLogic`、`@Version` 和 JSON TypeHandler 均需通过集成测试验证，特别关注批量更新与自定义 SQL 是否绕过插件。
8. Spring Boot 4.1.0 较新，Sa-Token/MyBatis-Plus 已选用 boot4 适配依赖；新增 Flyway、OCR SDK、对象存储或检索组件时需先验证 Java 21 和 Boot 4 兼容性。
9. 所有 BIGINT ID 返回前端时应避免 JavaScript 精度丢失；Vue/TypeScript 模型建议按字符串接收 ID。
10. 生产迁移必须具备数据库备份、文件清单与哈希校验报告，以及从新表回退到旧读路径的预案。
